# 合成示例：没有修好，但完成了诊断

> 这是用于演示协议的合成案例，名称和来源均为虚构，不能作为事实依据。

## 会话契约

- 入口：一个社区维修活动页面
- 预算：6 次有效跳转
- 模式：guided
- 检查频率：每 3 步
- 非目标：不要强行形成文章选题

## 探索轨迹

### 1. 活动页面 → 志愿者维修记录

- 观察：活动页链接到公开的维修尝试记录。
- 陌生细节：记录把结果分为“修好”“未修好”和“完成诊断”。
- 下一跳理由：“完成诊断”被当作一种结果，而不是维修失败。

### 2. 维修记录 → 接待表单

- 观察：表单会询问物主是否只需要“确认故障原因”。
- 推断：即使无法修复，一些人仍然需要理解故障。
- 下一跳理由：继续追这个服务类别，而不是搜索另一种维修技术。

### 3. 接待表单 → 志愿者培训说明

- 观察：结案前，志愿者要解释故障原因和后续选择。
- 人的干预：“不要把它写成维修权议题，继续追为什么解释本身也算服务。”

## 检查点

- 路线：公开活动 → 维修结果 → 接待类别 → 志愿者实践。
- 重复警告：全部来源都来自同一个组织。
- 人选择的路线：寻找设备没有修好时的物主第一手叙述。

### 4. 培训说明 → 物主论坛帖

- 观察：一名物主说，虽然设备无法恢复，但得知数据仍可取出后感到轻松。
- 不确定性：单个个人案例不能说明普遍情况。
- 下一跳理由：价值可能来自减少不确定性，而不是恢复设备功能。

### 5. 论坛帖 → 数据恢复检查表

- 观察：检查表把设备功能、数据访问和更换决策分开处理。
- 解释修正：“维修成功”不是单一的二元结果。
- 下一跳理由：查看维修社区是否记录这些非二元结果。

### 6. 检查表 → 社区结果分类

- 观察：分类包含诊断、安全处置、数据恢复、技能传递和成功修复。
- 新问题：为什么许多维修服务和统计仍把这些不同价值压缩成“修好 / 没修好”？

## 事后回看

入口只是一次维修活动，意外走出的路线却不是新维修技术，而是另一种结果模型：即使物件仍然损坏，诊断也可能减少不确定性、保护数据或改善更换决策。人的干预阻止了熟悉的政策框架过早吞掉探索。下一轮应离开这个合成环境，用真实组织资料检验是否存在类似结果分类。
